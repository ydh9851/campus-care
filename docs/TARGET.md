> 以下 3.1 – 3.5 为图片原文给定的功能点，逐条拆解为「原文要求 / 目标效果 / 实现要点 / 验收标准 / 现状差距」。

### 3.1 Agent Runtime Harness 设计

**原文要求：**
> 设计并实现 `AegisCareAgentHarness`，将 HTTP/SSE 接入层与 Agent 运行流程解耦，统一编排输入脱敏、Runtime 调用、消息与报告持久化、Agent Trace 记录和计划工具生成。

**目标效果：**
- 存在一个名为 `AegisCareAgentHarness` 的核心类/模块，作为**唯一的 Agent 执行入口**。
- 接入层（HTTP / SSE 路由）**只负责协议转换**，不含任何业务编排逻辑。
- Harness 内部按固定管线（Pipeline）顺序执行，每一步职责单一、可替换：

```
HTTP/SSE 接入
   └─► AegisCareAgentHarness.invoke(...)
          1. 输入脱敏       (PII 脱敏 / 敏感词预处理)
          2. Runtime 调用   (交给多 Agent runtime 执行)
          3. 工具后处理     (工具返回结果的归一化与校验)
          4. 消息与报告持久化
          5. Agent Trace 记录
          6. 计划工具生成   (plan → tool 的生成与登记)
```

**实现要点：**
- 接入层与 Harness 之间通过**入参/出参 DTO** 解耦，禁止路由函数直接调用 Agent 内部方法。
- 管线各阶段应是**可插拔节点**（middleware / hook 风格），新增阶段不改动已有阶段。
- SSE 与非 SSE 两种模式**共用同一条管线**，只在最外层输出方式上分叉。
- Trace 记录需包含：runId、各阶段耗时、调用的 Agent、工具调用序列、状态与错误。

**验收标准：**
- [ ] 全项目只有 Harness 一处调用 Agent runtime。
- [ ] 新增一个管线阶段，接入层零改动。
- [ ] 一次请求能拿到完整结构化 Trace（含阶段耗时与工具序列）。
- [ ] SSE 与普通请求走同一 Harness 路径，行为一致。

**现状差距（v1）：** 目前 `app/api/` 路由 → `app/graph/` LangGraph 直连，编排散落在路由与图节点中；无统一 Harness、无结构化 Trace、无「计划工具生成」概念。

### 3.2 多 Agent 协作（共享黑板 + 事件驱动）

**原文要求：**
> 针对校园心理与高危风险复核场景，设计基于共享黑板的事件驱动协作机制，由 Coordinator 任务认领、artifacts 发布和安全审查。

**目标效果：**
- 采用**共享黑板（Blackboard）**作为多 Agent 的公共工作区，Agent 之间**不直接互相调用**，只通过黑板读写 + 事件通信。
- **Coordinator** 负责：任务认领（claim）、任务分发、生命周期管理。
- Agent 产出的中间结果以 **artifacts** 形式发布到黑板，供后续 Agent 消费。
- 高危风险复核走**独立协作流程**：由多个 Agent（如风险研判 + 安全审查）交叉确认后才下结论。

**关键机制：**

| 机制 | 说明 |
|---|---|
| 黑板 | 共享状态存储，按 key/命名空间隔离，支持读写与订阅 |
| 事件驱动 | 状态变更发布事件，触发订阅该事件的 Agent 唤醒 |
| 任务认领 | Coordinator 下发任务，Agent 认领后置于执行中，避免重复消费 |
| artifacts 发布 | Agent 完成后将产物写入黑板并广播，附元数据（生产方、时间、置信度） |
| 安全审查 | 高危结论必须经过独立安全审查 Agent 复核 |

**验收标准：**
- [ ] Agent 之间无直接方法调用，通信全部经黑板或事件。
- [ ] 同一任务不会被两个 Agent 重复处理（幂等认领）。
- [ ] 高危结论有安全审查环节，且审查过程留痕。
- [ ] 黑板上的每个 artifact 可追溯生产方与消费方。

**现状差距（v1）：** 单 Agent 流程（LangGraph 四节点顺序/条件执行），无黑板、无 Coordinator、无多 Agent 交叉复核。

### 3.3 Engineering Harness 建设（回归与评测）

**原文要求：**
> 针对多 Agent、RAG 和工具链改动难以回归的问题，构建基于临时 SQLite 和内存记忆的一键验证脚本，覆盖 Risk Safety、Agent Routing、Standard Skills、RAG、API、Tool Queue 六大类核心链路。在 60 条固定评测集、TopK=4 条件下，Recall@K / HitRate 达到 **0.9667**，MRR 达到 **0.9083**。

**目标效果：**
- 一条命令跑完全部核心链路的**一键验证脚本**。
- 运行环境**不依赖外部服务**：用**临时 SQLite** 替代 MySQL、**内存记忆**替代 Redis/向量持久化，做到开箱即跑。
- 覆盖**六大类**核心链路：

| # | 类别 | 覆盖内容（推导） |
|---|---|---|
| 1 | Risk Safety | 关键词/否定/转述规则、高危判定、风险只升不降 |
| 2 | Agent Routing | 意图识别与路由分流是否正确 |
| 3 | Standard Skills | 内置标准能力（测评计分、报告生成等） |
| 4 | RAG | 检索命中与排序质量 |
| 5 | API | 接口契约、鉴权、统一返回体 |
| 6 | Tool Queue | 工具入队、调度、执行、失败处理 |

**量化指标（硬性验收）：**

| 指标 | 目标值 | 评测条件 |
|---|---|---|
| Recall@K | **0.9667** (= 58/60) | 60 条固定评测集，TopK = 4 |
| HitRate | **0.9667** | 同上 |
| MRR | **0.9083** | 同上 |

**验收标准：**
- [ ] `python xxx` 单命令可跑，无需启动 MySQL / Redis / 外部向量库。
- [ ] 六大类链路均有断言，且全部通过。
- [ ] 评测集固定为 60 条并纳入版本管理，指标可复现。
- [ ] 三项指标达到或超过目标值。
- [ ] 脚本可接入 CI（区别于需完整四件套的端到端脚本）。

**现状差距（v1）：** 有 `tools/verify_chain.py`（73 断言，端到端，需完整四件套，未进 CI）与 Java 侧 23 项单测；**无** SQLite/内存隔离的 Harness、**无** RAG 评测集与 Recall/MRR 指标。

### 3.4 上下文管理与压缩（分层记忆）

**原文要求：**
> 针对长对话导致历史上下文膨胀的问题，采用 Redis 优先、MySQL 回填的分层记忆机制，并结合历史裁剪、摘要生成和近期消息保留策略，将模型上下文控制在受控长度内。

**目标效果：**
- **分层记忆**：
  - **热层（Redis）**：最近对话，低延迟读取，**优先命中**。
  - **冷层（MySQL）**：完整历史，Redis 未命中时**回填**。
- **上下文压缩**：对长对话执行
  - 历史裁剪（超长历史按策略丢弃/合并）
  - 摘要生成（对远期历史生成滚动摘要）
  - 近期消息保留（近 N 轮原文完整保留，保对话质量）
- 最终送入模型的上下文长度**始终受控**，且有明确上限。

**验收标准：**
- [ ] Redis 命中时不再查 MySQL；未命中则回填 Redis。
- [ ] 长对话（超过阈值）仍能正常回复，模型上下文不超上限。
- [ ] 摘要能体现远期历史的关键信息（风险等级、关键事实不丢）。
- [ ] 上下文的组装过程可观测（命中层、裁剪条数、摘要长度）。

**现状差距（v1）：** 仅「历史硬截断 10 条」，无 Redis/MySQL 分层、无摘要、无裁剪策略。（见 README「待改进」P2）

### 3.5 MCP 与持久化队列

**原文要求：**
> 针对后台动作阻塞学生端流式回复的问题，将 MCP 工具接口、工具队列和埋点事件/运行轨迹写入 MySQL 任务表并沿进程内线程池异步执行；通过幂等入队、依赖调度与重试死信保障任务恢复与可追溯。

**目标效果：**
- **不阻塞主链路**：后台动作（工具调用、埋点、轨迹落库）全部异步化，学生端 SSE 流式回复不被阻塞。
- **MCP 工具接口**：工具以 MCP 协议暴露，统一注册与调用。
- **持久化队列**：工具队列、埋点事件、运行轨迹**写入 MySQL 任务表**（而非仅内存队列），进程重启可恢复。
- **执行模型**：**进程内线程池**异步消费，避免引入额外中间件。
- **可靠性三件套**：
  - **幂等入队**：同一任务重复入队只生效一次（唯一键/去重键）。
  - **依赖调度**：任务间有依赖关系时，按依赖顺序执行。
  - **重试死信**：失败任务按策略重试，超过上限进入死信，可人工/脚本重放。

**验收标准：**
- [ ] 后台动作耗时不影响 SSE 首字节与逐 token 输出。
- [ ] Java/Python 重启后，未完成任务可从 MySQL 恢复执行。
- [ ] 重复入队不产生重复执行。
- [ ] 有依赖关系的任务按序执行。
- [ ] 失败任务可见、可重试、有死信记录。
- [ ] 每个任务的运行轨迹可查（对应 3.1 的 Trace）。

**现状差距（v1）：** 无 MCP、无任务表、无队列、无死信；AI 调用失败无补偿（README 记为 P3「AI 失败无消息重发」）。

| 维度 | v1 现状（`campus-care`） | v2 目标（AegisCare） |

1. [ ] `AegisCareAgentHarness` 落地，接入层与运行流程完全解耦，SSE/非 SSE 共用管线。

7. [ ] 全链路 Trace 可查，任务可恢复、可追溯。

## 6. 给后续 AI / 协作者的工作约定

1. **先读本文档再动代码**；本文件是需求基线，与 README 冲突时以本文件为准（README 描述的是现状）。
2. **不要推倒 v1**：v2 是在既有 Java/Python/前端之上的演进，复用已有鉴权、落库、风险规则。
3. **安全红线不变**：
   - 风险等级「只升不降」；
   - 危机干预资源硬编码，不交给模型生成；
   - 高风险必过安全审查；
   - 心理数据属敏感个人信息，新增的 Trace / 任务表同样要遵守访问审计（谁在何时看过）。
4. **异步化不等于丢数据**：任何后台化动作都必须先落库再执行，保证可恢复。
5. **新增能力必须可回归**：每引入一类链路，同步补 Engineering Harness 断言。
6. **改动接口需同步更新** `docs/API.md`，改动启动方式需同步 `docs/SETUP.md`。
